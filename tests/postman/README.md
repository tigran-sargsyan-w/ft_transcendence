# WAF Security Evaluation — Postman

This directory contains a repeatable Postman collection for demonstrating and regression-testing the **Nginx + ModSecurity + OWASP Core Rule Set (CRS)** gateway in `ft_transcendence`.

The requests exercise normal traffic, suspicious HTTP payloads, protocol enforcement, and the scoped Engine.IO / Socket.IO polling exception. This is a **local development/evaluation tool**, not a penetration test of third-party systems.

## Contents

- `waf-security.postman_collection.json` — Postman Collection v2.1 with **33 requests in 10 folders**, including status-code assertions and an Engine.IO session test.

## Prerequisites

1. Start the trusted development stack and confirm it is healthy (`make health`).
2. Use **Postman Desktop** on a machine that can reach the configured domain and HTTPS port (and optionally the HTTP redirect port). Run `python3 -m scripts.dev.configuration` to read the public settings. On WSL/VS Code, check that the necessary ports are forwarded to the host.
3. Ensure the configured domain resolves to the appropriate local development host, and **trust the local `mkcert` root CA** in Postman/the operating system. Keep TLS certificate verification enabled.
4. Run these tests **only against your own authorized local development environment**. Do not point the collection at public or production services.

## Import and run

1. In Postman, select **Import** and choose `waf-security.postman_collection.json`.
2. Set the collection variables (the imported values intentionally start blank):

   | Variable | Configured value (no trailing slash) | Purpose |
   | --- | --- | --- |
   | `base_url` | `APP_ORIGIN` from the configuration command | HTTPS endpoint through the WAF |
   | `http_base_url` | `http://DEV_DOMAIN:DEV_HTTP_PORT` using the configured values | Optional HTTP-to-HTTPS redirect test |

3. Select a request and click **Send** to inspect the response and **Test Results**, or use the **Collection Runner** to execute the whole collection **in order**.
4. For **09 — HTTP redirect**, turn off **automatic redirect following** in Postman for that request/run so the original `308` response is visible.
5. For the live Engine.IO test, run **08.1** immediately before **08.1b**. Request 08.1 extracts a temporary `sid` into the collection variable `engineio_sid`; request 08.1b sends a legitimate polling POST using that SID. A SID can expire, so rerun 08.1 if necessary.

No authentication tokens, credentials, real user data, or secrets are needed. Do not commit Postman exports containing saved cookies or local credentials.

## Expected results

The following responses were observed on the local WAF development stack on **2026-11-17**. Changes to CRS versions, rules, application routing, or request encoding can change the results.

| Test group | Expected behavior |
| --- | --- |
| **00 — Baseline** | 4 normal requests return `200` |
| **01–05 — Attack-pattern probes** | SQLi, XSS, traversal, and command-injection patterns return `403` |
| **06 — HTTP protocol / policy** | `TRACE` → `405`; `text/plain` POST outside Socket.IO → `403`; benign JSON POST to a missing route → backend `404` |
| **07 — Additional CRS signatures** | Scanner fingerprint, CRLF, Log4Shell-style marker, and template-expression probes return `403` |
| **08 — Engine.IO / Socket.IO** | Polling handshake and a live-SID polling POST → `200`; invalid SID → backend/Engine.IO `400`; out-of-scope `text/plain` and polling-with-SQLi probes → `403` |
| **09 — HTTP redirect** | HTTP request returns `308` with a `Location` header pointing to HTTPS |

**Observed full-run summary (33 requests):** `22 × 403`, `6 × 200`, `2 × 400`, `1 × 404`, `1 × 405`, `1 × 308`.

A `403` response **alone does not identify the exact CRS rule** responsible. If an evaluator asks for proof of a specific detection, correlate the request with the ModSecurity audit/error log and its rule ID. A `404`, `405`, or `400` may be generated by Nginx or the application rather than ModSecurity.

These requests demonstrate **detection of suspicious request patterns**, not successful exploitation or proof that the backend contains SQLi, XSS, local-file-inclusion, command-injection, or Log4Shell vulnerabilities. The `/api/v1/health` endpoint is deliberately used as a harmless, repeatable target.

Some requests contain URL-encoded payloads. Postman may encode parts of the URL again; check the **Postman Console** when comparing exact payloads or investigating unexpected results.

## Engine.IO compatibility: important detail

Our gateway uses a narrowly scoped ModSecurity exception for CRS rule **920420** only when all of these match:

- Path: `/socket.io/`
- Method: `POST`
- Query parameter: `transport=polling`
- Content type: `text/plain` (optionally with UTF-8 charset)

This allows valid Engine.IO long-polling requests while retaining other CRS protections. The **08.5** probe verifies that SQLi-like input is still blocked on the polling route. The HTTP collection does **not** independently demonstrate a successful WebSocket Upgrade; show that separately in the browser's DevTools (Network → WS) or with an actual Socket.IO client.

## Suggested 42 evaluation sequence

Show a normal backend request (`00.3`), then one SQLi (`01.1`), XSS (`01.2`), traversal (`04.1`), command-injection (`05.2`), and scanner-signature (`07.1`) probe. Follow with benign JSON POST (`06.3`), the live Engine.IO handshake + POST (`08.1` → `08.1b`), and the SQLi-on-polling probe (`08.5`). Explain that **allowed traffic passes**, **recognized suspicious traffic is blocked**, and the **Socket.IO compatibility exception is limited**.

A regular Nginx reverse proxy without ModSecurity/CRS would typically forward many suspicious query strings to the backend instead of returning `403`, but actual outcomes depend on the Nginx and backend configuration. Do not present a hypothetical no-WAF result as a measured result.
